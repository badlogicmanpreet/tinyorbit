Inside the Agent Loop

One SWE-bench task, traced at the wire. Every HTTP stream event, every adaptive-thinking pause, and every byte of history resent between turns, recorded from a real run and replayed here.

task django__django-14672 model claude-opus-5 turns 19 SSE events – wall clock 60s cost $0.22
What this is. tinyorbit is a 1,100-line terminal coding agent. It was given a Django bug report inside a container and left alone. It read code, edited a file, wrote a test, ran the suite, and stopped. To document the loop, the transport was instrumented to append one JSON line per stream event, and the task was re-run with the model's reasoning summaries switched on. Everything below is that recording. No step is illustrative.
01

The loop

The harness owns the loop. The model never runs anything; it emits a request to run something, and the loop decides whether to honor it. One pass through these five stages is one turn. This task took nineteen.


  
The invariant that makes it work. Every tool_use block the model emits must be answered by a tool_result block with the same id, in the very next message. If the user interrupts mid-batch, the loop still synthesizes results for the unanswered calls before it exits. A history with an orphaned tool call is rejected by the API, so this is not politeness, it is the protocol.

04
Adaptive thinking on the wire

  

    
The harness asks for thinking: {type: "adaptive"} on every single call. It never asks for a fixed budget. The model decides per call whether to think at all, and it declined on fourteen of nineteen. Thinking appeared exactly where the work got confusing.

  

  

  

    
Those five summaries, in full, are the agent's actual reasoning at its five hardest moments:

  

  

  
What the socket is doing while the model thinks

  

    
This is the question the trace was built to answer. The sequence on a thinking call is always the same shape:

  

  

    
  

  

    The connection stays open and idle, then floods. The server sends message_start, then immediately content_block_start announcing a thinking block. Then nothing crosses the wire for –. The socket is open the entire time; no keepalive is needed at this scale and no timeout fires. When the model finishes reasoning, the whole summary lands in a burst of deltas averaging – apart. Across all 1,373 events in this task the median inter-event gap was –, and the longest was –, during that thinking pause.
  

  

    
So streaming here does not mean the reasoning trickles out as it is produced. It means the response is one long-lived HTTP body that the server writes into whenever it has something, and the client can act on partial content the moment it arrives. For the agent this matters most on the last call, where the answer text streams to the terminal token by token while the model is still writing it.

    
Two properties of thinking blocks are easy to miss and both are visible in the trace. The raw chain of thought is never returned by the API on this model: display: "summarized" yields a readable precis, and the default, "omitted", yields a block whose text is an empty string. Either way the block carries a cryptographic signature and is billed as output tokens. The harness must replay those blocks back verbatim on the next request, which it does by appending the response content unmodified.

  

  
A finding from this exercise. The ten-instance benchmark runs used the default, so every thinking block came back with empty text, and the terminal renderer that exists to display reasoning never fired once. Thinking still happened and was still billed. Turning on summaries cost nothing extra and made the agent's reasoning legible, which is why this capture uses it.






  
05
What gets resent every turn

  

    
The API is stateless. The model remembers nothing between calls, so the harness resends the entire conversation every time. Turn 19 shipped all thirty-seven messages again. The history grows by exactly two messages per turn: the assistant's reply, then one user message holding the tool results.

  

  

  

    
Resending everything should be ruinously expensive, and it would be without a prompt cache. The system prefix carries a cache breakpoint, and each turn's request is a strict extension of the previous one, so the shared prefix is served from cache at a tenth of the input price.

  

  

  

    Two tokens. On every one of the nineteen calls, uncached input was exactly 2 tokens while cache reads climbed from zero to 12,039. That number is the tell: input_tokens counts only what falls after the last cache breakpoint, so a steady 2 means the cache matched the entire prefix every time. Total billed input across the whole task was 12,039 cache reads plus 11,669 cache writes plus 38 fresh tokens.
  

  
Why the boundary is drawn where it is

  

    
Caching is a prefix match, so one changed byte anywhere before the breakpoint invalidates everything after it. The system prompt is therefore split in two.

  

  

  

    
Identity, tool guidance and the working directory are fixed for the session and sit above the line. Today's date sits below it, because a prompt that interpolates a clock into its cached block silently destroys its own cache on every call. This is the single most common way a cache hit rate collapses.

    
There is a second, larger layer the harness would reach for if this task had run long enough. Above 150,000 context tokens it asks the model to summarize the conversation and replaces the history with that summary. It also catches a prompt-too-long error, compacts once and retries. Neither fired here. The largest request in this task was about 12,000 tokens, roughly one percent of the window.

  






  
06
Coming back down

  

    
When the stream closes with stop_reason: "tool_use", control returns to the harness. It groups the calls, checks each against the permission policy, runs them, and formats the output back into the shape the API expects.

  

  

  

    
The model asked for a single tool per turn on all eighteen tool turns, so the concurrency machinery never engaged. It exists: consecutive calls are partitioned into groups, and a group whose members are all concurrency-safe runs under one gather. A Bash command is classified by splitting on pipes and && and checking that every segment starts with a known reader and carries no redirect, which decides both whether it needs permission and whether it may run in parallel.

    
Under bypassPermissions, used here because the container is disposable and nobody is watching, the permission chain short-circuits before it consults any rule. In an interactive session the same call would stop and ask.

  

  
The detour worth reading. Turns 5 through 12 are the agent failing to run Django's test suite. It tried the system Python, then the repository root, then a PYTHONPATH override, then went looking for interpreters, and finally found the conda environment at /opt/miniconda3/envs/testbed. Eight turns, roughly forty percent of the task, spent on an environment detail no line of the prompt mentioned. Its own reasoning on turn 9 shows it forming the hypothesis that led out.






  
07
How it ends

  

    
Every turn's exit is decided by one field. stop_reason came back as tool_use eighteen times and end_turn once, and that nineteenth call is the only one whose content held no tool call. No tool call plus no pause means the work is finished: the loop emits a terminal event carrying the full message history and returns.

  

  

  

    
The other terminal reasons never fired here but shape the design. An output cut off at the token cap is retried once at a larger cap, then nudged with a continue instruction up to three times. A refusal is terminal and carries its category. An interrupt while streaming exits immediately; an interrupt during tools exits only after every orphaned call has been answered. A turn counter caps the whole thing at sixty.

08
Reading the trace yourself

  

    
The instrumentation is a single environment variable. Setting it makes the transport append one JSON line per stream event; leaving it unset costs nothing.

  

  

  

    
Each line carries a millisecond offset from the request, the event type, the delta type, its character count and its text. Request lines additionally carry the full shape of the history about to be resent, every message as a role plus its block types and sizes, which is where the context figures on this page come from. Response lines carry the usage ledger and stop reason.
